# PRD｜小药盒 · 家庭用药提醒

> 版本 v1.0 ｜ 主理人：商见成 ｜ 定位：可广告变现的自有垂类工具小程序
> 本文档为设计、前端、后端、增长四条线的统一输入，后续专业方案必须严格对齐本文档的 MVP 边界与合规红线。

---

## 一、一句话产品定义

**给家里有慢病老人的子女用的「远程用药提醒 + 服药打卡」小程序：子女在微信里设好提醒，老人到点收到提醒，吃完了点一下，子女能看到「今天吃了几次」。**

不是药品电商，不是在线问诊，不做诊断建议 —— 只做**提醒 + 记录 + 家属可见**这三件事。

---

## 二、为什么选这个赛道（决策依据）

用户已明确的三个前提：**垂类实用工具 / 广告流量主变现 / 自己能写代码**。

这三条组合起来，产品必须同时满足四个硬条件，缺一不可：

| 硬条件 | 为什么必须 | 小药盒是否满足 |
|---|---|---|
| 每天都会打开 | 广告收入 ≈ 曝光量 × eCPM，低频工具永远赚不到钱 | ✅ 慢病用药每天 1–3 次，刚性 |
| 一个家庭多个用户 | 广告按用户计曝光，单用户带 2–3 人是最便宜的获客 | ✅ 子女设置 + 老人接收 + 兄弟姐妹协同 |
| 有自然搜索流量 | 没预算投流，只能吃微信「搜一搜」的长尾词 | ✅ "吃药提醒""用药提醒""老人吃药"搜索意图极明确 |
| 无资质门槛 | 医疗类目审核严，个人主体做不了问诊/处方 | ✅ 纯提醒工具，不入医疗类目，不涉诊疗 |

### 竞品缝隙（真实存在的空位）

- **药企/连锁药店小程序**：核心是卖药，提醒是附属功能，且绑定自家药品库，老人不爱用。
- **手机自带闹钟**：只能响，不记录、不通知家属、不吃药没法反馈。
- **健康管理类 App**：太重，老人装不上、不会用、还要注册登录。
- **微信内的同类小工具**：普遍是"单人吃药打卡"，没有做**家庭协同**这一层 —— 而这恰恰是子女愿意主动传播的动力。

**我们的缝隙 = 家庭协同。** 老人自己不会装小程序，但子女会。子女装完必然要拉人（爸妈、兄弟姐妹），一次获客带来 2–3 个用户。这是本产品最核心的增长杠杆，也是所有设计决策的锚点。

## 三、目标用户

### 主用户（决策者 + 付费者）
- 30–45 岁，一二线到三线城市，父母 60+ 有高血压/糖尿病/心脏病等慢病
- 痛点：不在父母身边，天天打电话问"药吃了没"很烦，父母还会骗人说吃了
- 行为：微信重度用户，愿意为"安心"付出小钱

### 使用用户（每日触点）
- 60–75 岁老人，会用微信语音和视频，但抗拒复杂 App
- 核心要求：**字要大、按钮要大、一步到位、别让我选**
- 接收方式优先级：微信订阅消息 > 小程序内提醒 > 短信（成本高，MVP 不做）

### 次要用户
- 兄弟姐妹（协同查看，分摊照护责任，也是天然的二次传播节点）

## 四、核心场景（用户旅程）

**场景 A｜首次设置（子女操作，3 分钟内完成）**
子女打开小程序 → 微信一键登录 → 添加"服药人"（爸爸）→ 添加药品（药名可手写/拍照，剂量、频次）→ 生成提醒时间表 → 分享给爸爸和兄弟姐妹 → 各自点开即加入家庭。

**场景 B｜每日提醒（老人操作，5 秒内完成）**
到点 → 微信服务通知弹出"该吃降压药了（1片）"→ 点开小程序 → 大字卡片 + 一个大按钮「我已服用」→ 点击完成 → 记录入库，家庭其他成员可见。

**场景 C｜漏服兜底（价值最高的一环）**
超过设定时间 60 分钟未打卡 → 自动推送提醒给"家庭管理员（子女）"：**"爸爸今天 8:00 的降压药还没吃"**。这一条推送就是用户留下来的理由，也是分享传播的话术。

**场景 D｜周报回顾**
每周日晚推送"本周服药完成率 92%，漏服 3 次（周三早、周五晚…）"，可转发到家庭群。

## 五、MVP 功能范围（第一版必须做 / 明确不做）

### 必须做（P0，4–6 周单人可完成）

1. **微信登录 + 家庭组**
   - 一个用户可创建/加入多个家庭组；家庭内有「管理员」与「成员」两种角色
   - 邀请方式：分享卡片进群或私聊，被邀请人点击即加入（不做邀请码输入，老人不会输）

2. **服药人档案**
   - 姓名、称呼（爸/妈/爷爷）、头像（可选）
   - 一个家庭组支持多个服药人（应对父母双方）

3. **药品与计划管理**
   - 药品：名称（支持手写输入 + 常用药快捷选择）、规格、备注、默认剂量
   - 计划：每日 N 次，按时间点设置（早/中/晚快捷模板 + 自定义时间）
   - **剂量按时间点独立设置**（v1.2 修订）：降压缓释片、优甲乐、华法林等常见"早 1 片、晚半片"的吃法，单剂量模型表达不出来，会导致老人按错误剂量服药且系统不报错。每个时间点携带自己的剂量，默认继承药品默认剂量，子女不改即为统一剂量，不增加操作步骤。
   - 支持"周期用药"（连续 30 天后自动结束）与"长期用药"

4. **提醒与打卡**
   - 订阅消息推送（关键：必须引导用户完成一次性订阅授权，见技术约束）
   - 打卡页：超大字号卡片 + 单个主按钮「我已服用」
   - 支持"稍后提醒（15 分钟）"与"今天不吃（跳过并记原因）"

5. **漏服预警**
   - 超时 60 分钟未打卡 → 推送管理员

6. **家庭看板**
   - 今日：每位服药人的每次用药状态（待服/已服/漏服/跳过）
   - 本周完成率 + 连续达标天数

7. **广告位**（变现核心，见第六节）

8. **基础设置**：提醒音开关、免打扰时段、隐私政策与用户协议

### 明确不做（第一版砍掉，防止范围爆炸）

- ❌ 药品数据库/条码扫描识别（数据合规风险 + 成本高，改为手写 + 常用药预设）
- ❌ 在线问诊、用药建议、相互作用检查（**医疗合规红线，个人主体绝对不能碰**）
- ❌ 药品购买/电商跳转（涉及资质与售后）
- ❌ 血压血糖数据记录（第二版增值点，先验证核心留存）
- ❌ 语音提醒自定义、家属视频通话（伪需求，成本高）
- ❌ 多端同步（App/H5），只做小程序

## 六、盈利模型（广告为主，这是本方案最关键的一节）

### 6.1 现实校准（必须先说清楚）

流量主收入 = **广告曝光量 × eCPM / 1000**。微信小程序广告位的真实 eCPM 区间：

| 广告形式 | 实际 eCPM 区间 | 说明 |
|---|---|---|
| Banner | 1–5 元 | 最低，只能当补充，不能当主力 |
| 插屏 | 5–15 元 | 页面切换时触发，注意别打断打卡 |
| 激励视频 | 30–80 元 | 单价最高，但需要给用户"看的理由" |

**结论：只挂 Banner 的产品永远赚不到钱。** 小药盒的广告结构必须是「插屏为主 + 激励视频为辅 + Banner 兜底」。

### 6.2 广告位设计（4 个位置，均不打断核心流程）

| 位置 | 形式 | 触发时机 | 设计理由 |
|---|---|---|---|
| A. 打卡成功页 | Banner | 点击「我已服用」后停留页底部 | 用户此刻心情正向，容忍度最高，且必然停留 2–3 秒 |
| B. 首页家庭看板 | 原生模板 Banner | 首屏底部固定 | 每日必看页，稳定曝光基本盘 |
| C. 药品详情 → 返回 | 插屏 | 从药品详情返回列表时 | 非关键路径，频次可控（设 30 秒冷却 + 每日上限 3 次） |
| D. 周报页解锁 | 激励视频 | 想看"详细漏服分析/历史趋势"时 | 给用户明确理由：看 15 秒视频换详细报告 |
| E. 新增药品第 4 个起 | 激励视频 | 免费用户药品数上限 3 个 | 天然的付费/看广告分岔口 |

**广告体验铁律**：打卡主流程（提醒弹窗 → 打卡按钮）**零广告**。这条不能破，否则老人一怒卸载，留存直接崩。

### 6.3 收入测算（保守/中性/乐观三档）

假设人均日曝光：Banner 5 次、插屏 1.5 次、激励视频 0.3 次。

| 指标 | 保守 | 中性 | 乐观 |
|---|---|---|---|
| DAU | 3,000 | 10,000 | 30,000 |
| 日曝光（Banner/插屏/激励） | 15k / 4.5k / 0.9k | 50k / 15k / 3k | 150k / 45k / 9k |
| Banner 日收入（eCPM 2/3/4） | 30 元 | 150 元 | 600 元 |
| 插屏日收入（eCPM 6/9/12） | 27 元 | 135 元 | 540 元 |
| 激励日收入（eCPM 35/50/65） | 31 元 | 150 元 | 585 元 |
| **日收入合计** | **≈ 88 元** | **≈ 435 元** | **≈ 1,725 元** |
| **月收入** | **≈ 2,600 元** | **≈ 13,000 元** | **≈ 52,000 元** |

**关键判断：广告变现的生死线是 DAU 1 万。** 达到 1 万 DAU 约需累计用户 8–12 万（工具类 DAU/MAU ≈ 30%，MAU/累计 ≈ 35%）。

> **v1.2 收入修正（以增长线复算为准，上表数字整体下调 15–20%）**：上表假设插屏 1.5 次/人日，但按 UI 定稿的四重频控（30 秒冷却 + 日上限 3 次 + 20:00–07:00 免打扰 + 打卡后 10 分钟内不弹）叠加"仅在药品详情返回时触发"这条低频路径，真实只能跑到 0.5–0.8 次/人日；Banner 也从 5 次下修到 4.3 次。
> **修正后中性档：DAU 1 万 ≈ 9,000–11,500 元/月**（原 13,000 元）。差额只能靠扩充激励视频场景（复诊报告导出等）补，**不能靠加广告位** —— 加位会伤留存，而留存决定 DAU 能不能到 1 万。
> 另需注意：流量主结算代扣个税（个人按劳务报酬预扣），**做现金流时按账面 80% 折算**。

### 6.4 变现结构（v1.2 重写：原"会员订阅"方案作废）

> **硬约束**：个人主体小程序**无法申请微信支付商户号**（需营业执照）。原方案里的「免广告会员 9.9 元/年」「家庭版 19.9 元/年」在当前主体下**卖不了**，全部作废。
> 这不是妥协，是唯一可行解：广告流量主正是个人开发者唯一不需要资质就能变现的通道。

**替代方案：所有"付费权益"改为「看激励视频解锁」。**

| 原设想权益 | 改为 | 说明 |
|---|---|---|
| 免广告会员 | ❌ 取消 | 无法收款。广告开关只能走远端配置，不做付费去广告 |
| 无限药品（第 4 个起） | 看 15 秒视频再加 1 个 | 广告位 E，同时是天然的"愿意看广告"筛选 |
| 周报详细分析 | 看 15 秒视频解锁 | 广告位 D，收入最高的一位（≈3,300 元/月 @DAU 1万） |
| 历史数据永久保存 | 看视频解锁「历史明细永久保存」 | 归档策略：明细保留 90 天（免费）/ 聚合数据永久 / 解锁后明细永久 |
| （新增）复诊报告导出 | 看 15 秒视频导出近 30 天记录 | 慢病家庭周期性刚需，是把激励视频观看率从 0.22 提到 0.33 的核心场景 |

**这套设计的两个好处**：
1. 用真实的"解锁率"验证付费意愿 —— 数据好再决定要不要办执照收真钱，试错成本为零。
2. 表结构（`orders` + `entitlements`）按未来接支付的样子建好，接支付时只加一个回调函数，业务代码零改动。

**如果以后要收真钱，必须做三件事**：① 办个体工商户执照（约 500–1,500 元，5–10 个工作日）② 用执照申请微信支付商户号 ③ 校验小程序主体与商户主体一致性（不一致会被拒）。做完之后，权益发放**必须改成支付回调驱动，绝不能沿用前端凭证模型** —— 激励视频的"看完"无法在服务端校验（微信无服务端回调），凭证可伪造；支付回调则是可信的。

> **收入结构：100% 广告。** 没有第二收入来源，这正是 DAU 1 万这条线如此关键的原因。

## 七、关键指标与验证假设

### 北极星指标
**周活跃家庭组的「打卡完成率」** —— 完成率低于 60% 说明产品没用，高于 80% 说明留住了。

### 漏斗指标
| 环节 | 目标 | 说明 |
|---|---|---|
| 打开 → 完成首次设置 | ≥ 45% | 设置流程超过 3 分钟就要重做 |
| 设置完成 → 邀请至少 1 人 | ≥ 50% | 家庭协同是本产品命门 |
| 被邀请 → 完成首次打卡 | ≥ 70% | 老人端操作必须 5 秒内完成 |
| 次日留存 | ≥ 35% | 工具类健康线 |
| 7 日留存 | ≥ 20% | |
| 30 日留存 | ≥ 12% | 慢病长期用药，理论上应该更高 |
| 打卡完成率 | ≥ 75% | |

### 三个必须验证的假设（MVP 上线 4 周内看数据）
1. **家属协同真的会发生吗？** 若邀请率 < 30%，产品退化为单人提醒工具，增长逻辑崩塌 → 需重新设计分享动机。
2. **老人会不会讨厌订阅消息？** 若订阅授权率 < 40%，提醒触达失效 → 需改走"子女代持账号 + 电话兜底"。
3. **广告位会不会杀留存？** 若加广告后 7 日留存下降超 15%，立即撤掉插屏，只留激励视频。

## 八、合规红线（个人主体必读，踩线直接封号）

1. **类目选择**：选「工具 - 效率」或「工具 - 健康管理（如可选）」，**绝不选「医疗服务」**。个人主体无法提供《医疗机构执业许可证》。
2. **文案禁区**：不出现"治疗""疗效""推荐用药""替代医生""根据症状判断"等表述。产品定位是"提醒工具"，不是"医疗建议"。
3. **免责声明**：首次使用必须弹窗确认"本工具仅提供服药提醒服务，不提供任何医疗建议，用药请遵医嘱"。
4. **数据合规**：药品名与用药记录属敏感健康信息，必须明示《隐私政策》，仅存于云端且与 openid 绑定，不对外共享、不做用户画像出售。
5. **广告合规**：医疗、药品、保健品广告不得出现在本小程序（流量主后台可设置行业屏蔽，必须开启）。
6. **订阅消息合规**：一次性订阅必须由用户主动点击授权，不得诱导、不得批量静默请求。

## 十、给下游三条线的明确输入

- **设计线（颜如绘）**：必须解决"双端双模"——同一个产品，子女端要信息密度，老人端要极致大字。请给出双主题方案与打卡页视觉稿说明。
- **前端线（程前锦）**：原生框架，包体积要小（老人机性能差），重点解决订阅消息授权时机、离线打卡兜底、广告位不阻塞渲染。
- **后端线（云栖梧）**：**技术栈已定（2026-10-29 主理人决策）：自建 .NET 10 + EF Core + PostgreSQL，禁用 EF 迁移、建表改字段走顺序递增 SQL 脚本，后端 TDD 开发**（详见 `docs/后端技术方案.md`）。重点设计提醒调度机制（时间轮物化 + `due_ts` 索引 + 三道幂等，执行器改为 .NET `BackgroundService`）、JWT 信任根与家庭组权限模型、以及成本随 DAU 增长的曲线（自建上线成本见总方案 §3.1）。
- **增长线（增之翼）**：冷启动不靠投流，靠搜一搜长尾词 + 家庭群裂变 + 老年健康内容号合作。请给出 0→1000 UV 的具体打法。

**主理人批注**：这个产品的成败不在功能多少，而在两件事 —— **老人愿不愿意每天点那个按钮**，以及**子女愿不愿意把卡片发到家庭群**。所有设计取舍都以这两条为准。
