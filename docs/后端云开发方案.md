## 一、技术选型结论

**结论：微信云开发（云函数 + 云数据库 + 云存储 + CDN），不做自建服务器。**

| 对比项 | 微信云开发 | 自建服务器（阿里云/腾讯云 1C2G） |
|---|---|---|
| 首年现金成本 | 0–20 元/月（免费额度内几乎为 0） | 服务器 60–100 元/月 + 数据库 40 元/月 |
| 域名与 ICP 备案 | **不需要域名，免备案** | 必须域名 + ICP 备案 + HTTPS 证书，2–3 周 |
| 微信登录 | `cloud.getWXContext().OPENID` 一行拿到，**无法伪造** | 需自建 code2session + session_key 自己的 token 体系，防重放/防伪造全部自理 |
| 订阅消息下发 | 云函数内直接调 `subscribeMessage.send`，无 IP 白名单 | 需配服务器 IP 白名单 + access_token 中控（多实例并发刷新会互相踢掉） |
| 运维 | 无（无 SSH、无补丁、无中间件） | 单人开发 4–6 周节奏下，运维会直接吃掉交付时间 |
| 扩展性上限 | 单环境 1000 并发实例，够 DAU 5 万；再往上可换 CloudBase 同源方案 | 天花板更高，但本项目 3 年内到不了 |
| 锁定风险 | 迁移成本中等，数据可导出 JSON | 无 |

**决定性理由三条**：
1. 个人开发者 + 单人 4–6 周节奏，**备案和运维是唯一会真正拖死项目的东西**，云开发把这两件事直接归零。
2. 广告变现的生死线是 DAU 1 万（PRD 6.3），而 DAU 1 万时的云开发月成本约 20–30 元 —— 成本根本不是变量，**别为省钱牺牲交付速度**。
3. 云开发的 `OPENID` 由服务端注入，是家庭组权限模型的信任根；自建方案要自己造这套，出错就是越权事故。

**唯一的自建理由**（明确记下，暂不触发）：需要跑长耗时任务（>60s，如批量 OCR）或需要 Redis 队列。当前 P0 都不需要。

## 二、整体架构

```
小程序端（原生）
   │  wx.cloud.callFunction  ── 全部业务写操作走云函数（无直连数据库写权限）
   ▼
┌─────────────── 云函数层（18 个）───────────────┐
│ 业务 API（11 个，严格按契约冻结表）│ 内部（7 个）│
│ user / family / patient           │ materializer │
│ medicine / plan / schedule        │ reminder-tick│
│ checkin / notify / ad / report    │ push-worker  │
│ config                            │ weekreport   │
│                                   │ archive      │
│                                   │ stats        │
│                                   │ warmup       │
└───────────┬───────────────────────┴──────────────┘
            ▼
   云数据库（MongoDB 兼容）          云存储 + CDN
   23 个集合，明细表 90 天归档        药品照片 / 头像（≤60KB 压缩）
            │
            ▼
   微信开放接口：subscribeMessage.send / code2session / 内容安全 msgSecCheck
```

**两条铁律**
- 前端**只能读** `users`（自己的）与 `medicines_common`（常用药预设），其余集合前端可读性设为 `false`，全部经云函数。
- 所有涉及 `family_id` 的入参，一律在云函数内用 `assertMember()` 校验，**前端传什么 openid 都不信**。

## 三、数据模型

### 3.0 两条全局约定（踩过坑才写得出）

1. **时区**：云函数 `new Date()` 是 UTC，定时触发器按北京时间触发。所有时间戳字段统一存 UTC 毫秒数（`_ts` 后缀），只有"自然日"字段 `due_date` 用东八区字符串 `YYYY-MM-DD`，由工具函数 `bjDate(ts)` 生成。**混用会导致早上 8 点的提醒跑到前一天。**
2. **日期字段一律存 `Number`（毫秒）而非 `Date`**，跨端序列化更稳，索引效率相同。

**`self_openid` 与渲染 `mode` 的关系（per-family，不能存在 user 上）**
```
mode = patients.where(self_openid == 当前 openid).非空 ? "elder" : "guardian"
```
- 同一个人在不同家庭组可以是不同身份（自己家 guardian、父母家 patient），所以 `mode` **必须按 fid 现算并随 `family.info` / `family.list` 返回**，绝不落到 `users` 上。
- **`mode` 只管渲染主题，`role` 才管权限，两者解耦**：一个人可以是 `role:"admin"` + `mode:"elder"`（自己吃药且管着全家），这时打卡页走老人主题，但设置页仍有管理员入口。
- 一个家庭多个服药人时，`elder` 只看到 `self_openid` 对应的那一个患者（其余患者仍由 guardian 视角管理）—— **这是设计红线，不是功能偏好**。
- 出参同时给 `selfUids[]`（数组，应对"一个人被误绑两个患者记录"的脏数据）与 `selfUid`（取第一个，兼容单值写法）。前端按数组过滤、单值兜底。

### 3.6 plans
| 字段 | 类型 | 说明 |

| `_id` | string | |

| `advance_min` | number | 提前量 0/5/10 分钟 |
| `created_by` / `updated_at` | | |

**`slots` 的三个设计约束（主理人已定稿）**
1. **主键规则不变**：`dose_logs._id` 仍用 `${plan_id}_${date}_${due_minute}` —— 分钟数天然区分时间点，`slot.key` 只是展示层标识，**不进主键**。这样"改时间点"= 生成新行 + 删除旧未到点行，语义清晰。
2. **不做"是否不同剂量"的开关**：新建药品时每个 slot 的 `d` 默认继承 `default_dose`，子女不改就是"早晚同剂量"，零额外认知负担。多一个开关就多一个老人看不懂的界面。
3. **老数据兼容**：只有 `default_dose`、无 `slots` 的计划，`materializer` 按"每个时间点都用 default_dose"补齐，**不写迁移脚本**（当前未上线，无真实老数据；此条为将来改结构时留的规则）。

索引：`status + start_date`（materializer 扫描）、`family_id + patient_id`、`patient_id`、**`medicine_id`（唯一）—— 契约是「1 药品 : 1 计划（含多 slot）」，多 slot 落在同一计划的 `slots` 数组里，不要为同一药品建多条计划，否则 materializer 会生成重复剂量**
增长：服药人 × 1.4 ≈ DAU 1 万时约 7,300 条。

### 3.7 dose_logs ★ 核心表，量最大
| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | **`${plan_id}_${due_date}_${due_minute}`** ← 确定性主键，**调度幂等的第一道锁**，同时作为前端 `dose_id` 暴露 |
| `family_id` / `patient_id` / `plan_id` / `medicine_id` | string | |
| **`dose_text`** | string | **该 slot 展开后的剂量展示串快照**（如"0.5片"）。**必须快照，不能 join 现算**：子女后期改剂量，历史记录要显示"当时吃的是多少"，这是用药史可追溯性 |
| `med_name_snapshot` | string | 药名快照，药品改名/删除不影响历史 |
| `due_date` | string | `2025-01-15`（东八区） |
| `due_minute` | number | 480 |
| `due_ts` | number | UTC 毫秒，**扫描索引主键** |
| `status` | string | **只允许 4 值：`pending` / `taken` / `missed` / `skipped`**（与前端 store 的 status 枚举严格一致，前端用 switch 渲染状态色）。迟到服用仍记 `taken`，另存 `is_late` 布尔供周报统计 —— **不要新增 `late` 状态值，会让前端 switch 落到 default 分支** |
| `taken_at` / `taken_by` | number/string | |
| `is_late` | bool | 超过 `due_ts+60min` 才打卡 |
| `skip_reason` | string | 老人选"今天不吃"的原因 |
| `snooze_count` | number | 稍后提醒次数，上限 2（超过返回 `429`） |
| `remind_status` | number | `0`未推 `1`已推 `2`推送失败 `3`无额度降级 |
| `remind_at` / `remind_errcode` | number | |
| `alert_status` | number | `0`未通知管理员 `1`已通知 `2`通知失败 |
| `alert_at` | number | |
| `week_key` | string | `2025-W03`，周报聚合用 |

索引（**建索引是本节唯一必须严格执行的事**）：
1. `due_ts + status + remind_status` ← **reminder-tick 每分钟扫描，决定整个系统性能**
2. `family_id + due_date` ← 家庭看板
3. `status + alert_status + due_ts` ← 漏服兜底扫描
4. `patient_id + week_key` ← 周报
5. `due_date` ← 归档清理

增长：DAU 1 万 × 人均 2.5 次 ≈ **13,000 条/天，39 万条/月**。
**归档策略：三档（已按主理人定稿。原 PRD 的"会员数据永久保存"因无法收款而失效，改为下述三档）**

| 档 | 对象 | 保留期 | 说明 |
|---|---|---|---|
| ① 明细（免费默认） | 普通家庭的 `dose_logs` | **90 天** | 超期先聚合成 `weekly_stats` 再删明细 |
| ② 聚合数据 | 全体家庭的 `weekly_stats` | **永久** | 完成率 / 连续达标的历史曲线不受影响，删的只是逐条明细 |
| ③ 历史明细永久保存 | 看激励视频解锁的家庭 | **永久** | `ad.unlock{product_id:'HISTORY_FOREVER'}` 发放，**权益记在家庭级** |

**`archive` 的删除条件（必须按此实现，不能只按日期删）**：
```
待删 = dose_logs.where(due_date < today-90)
                    .and(family_id NOT IN 持 HISTORY_FOREVER 的家庭集合)
顺序：先按 (patient_id + week_key) upsert 进 weekly_stats → 确认写入成功 → 再删明细
```
三个工程细节：
1. **家庭级权益**：记在 `families.history_forever_at`（不是 openid 级）。历史数据是全家共看的，一个成员解锁全家都该保住；解锁动作限 `admin` 触发。
2. **先聚合、后删除，不可反序**；聚合失败必须中止删除（宁可多占空间，不可丢数据）。删除分批 500 条/次，避免单次超时。
3. **不归档的后果**：1 年 470 万条、约 2.8GB，看板查询开始变慢，是第一个会爆的地方。`archive` 函数**必须在 M1 上线**，不能留到"以后优化"。

### 3.10.1 若要收真钱：完整升级路径（可选，非死路）

个人主体做不了支付，但这不是死路，是一条**有明确成本和时间表的可选升级**。写清楚，让主理人自己判断什么时候值得走。

| 步骤 | 动作 | 周期 | 费用 |
|---|---|---|---|
| ① | 办**个体工商户营业执照**（线上全程电子化，需经营场所证明；多地支持集群注册/住宅改商用） | 3–7 工作日 | 自办 0 元，代办 500–2,000 元 |
| ② | 经营范围**必须含**"信息技术服务 / 软件开发 / 互联网信息服务"，否则后续类目校验不过 | 含在①内 | — |
| ③ | 小程序**主体变更**为个体户（个人→个体户） | 1–2 周 | 微信审核 300 元 |
| ④ | 微信认证（企业/个体户必须） | 3–5 工作日 | 300 元/年 |
| ⑤ | 申请**微信支付商户号**（营业执照 + 法人身份证 + 结算账户） | 1–5 工作日 | 0 元，费率 0.6% |
| ⑥ | 类目与主体一致性校验：类目必须与经营范围匹配，**仍只能选「工具-效率」，绝不碰医疗类目** | 1 次审核 | — |
| ⑦ | 记账报税（个体户也要，**这是隐性大成本**） | 长期 | 200–400 元/月 |

**总周期**：已有执照 2–4 周；从零开始 4–8 周。**总年成本 ≈ 3,000–8,000 元**（记账占大头）。

**关键取舍（请主理人算这一笔）**：
> 年成本 5,000 元 ÷ 9.9 元/年 = **需要 505 个付费用户才能打平**。
> 按 PRD 6.4 的 2% 付费率，DAU 1 万（MAU 3.3 万）对应约 660 付费用户 → 年收入 6,534 元，**刚过打平线**。
> **结论：DAU 1 万是"办照收款"的经济性临界点。低于 1 万，记账成本会吃掉会员收入，不如继续只做广告 + 激励视频解锁。**

**两个必须避开的坑**：
1. **不要"先个人主体上线、以后再迁移"**。小程序主体变更需要重新认证 + 走迁移流程，且要保证 AppID 不变（AppID 不变 → `openid` 不变 → 用户数据不用迁移，这是唯一的好消息）。但迁移期间审核不通过会导致小程序不可用，对已上线的产品是致命的。**若已确定要收款，M0 就用个体户主体注册。**
2. **主体变更后仍不能碰医疗类目**。营业执照的经营范围不会让"用药建议"变得合法 —— PRD 第八节的文案禁区在个体户主体下**一条都不放松**。

**代码侧影响：零。** `orders.channel` 加一个枚举值 `wxpay`，新增 `pay_notify` 云函数（支付回调 + 验签 + `entitlements` 发放），`entitlements` 表结构不动。这就是第 12 节说的"留口子"。

### 3.12 dose_views（已读回执，增长 P1/W6）

老人真正的动机是"不给儿女添麻烦"和"我还行"，不是勋章积分 —— **"被看见"才是有效激励**。这张表只为一个界面服务：老人端打卡后第二天的一行灰字「昨天女儿看了你的记录」。

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | **`${fid}_${date}_${viewer_openid}`** ← 天然去重，**同一人同一天只看写一次**，避免看板每开一次就写一次 |
| `fid` / `date` | string | |
| `viewer_openid` | string | 看的人 |
| `viewer_role` / `viewer_alias` | string | `admin`/`member`/`elder` + 称呼（"女儿"），**用于生成那行文案** |
| `viewed_at` | number | 首次查看时间 |

**两个接口都不改**，指标也不丢。**但前端必须每次弹窗都上报，无论用户点了接受还是拒绝** —— 否则授权率会永远显示 100%，PRD 假设 2（<40% 则触达失效）就永远验不了。给增长侧的提醒：**两周后如果你看到授权率是 100%，那不是好消息，是采集坏了。**

> 为什么不能只更新主表：完成率是北极星指标，而 `correct` 是**唯一能人为改变它的入口**。审计必须独立、不可被主表更新掩盖。

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | 自动 |
| `dose_id` / `fid` / `uid` | string | |
| `operator_openid` / `operator_role` | string | 谁改的（必填，`elder` 根本进不来） |
| `from_status` / `to_status` | string | `taken` → `missed\|skipped` |
| `reason` | string | 可空 |
| `corrected_at` | number | |
| `week_key` | string | 聚合进 `weekly_stats.manualCorrectCount` 用 |

索引：`dose_id`、`fid + week_key`、`operator_openid + corrected_at`
增长：低频（只有纠错时写），可永久保留 —— **这恰好是"用药史可追溯"的一部分，archive 不得删它**。

**`dose_logs` 为此新增的三个字段**
| 字段 | 类型 | 说明 |
|---|---|---|
| `is_corrected` | bool | 是否被人工改过。**`schedule.today` 行尾「已修改」灰字用；也是"防来回刷"的判据** |
| `checked_by` | string | `self` / `manual`。**这是判断数据可信度用的，不是统计用**：将来若走"子女代持账号"，`self` 会骤降、`manual` 飙涨，完成率会"看起来还行" —— 不看这个分布，就会拿一个被人工修改抬起来的数字去判断产品健康度，比没有数据更危险 |
| `corrected_at` | number | 最后一次人工改判时间 |

**状态机的最终口径（吸收了 UI v1.2 的更正，比冻结表字面更精确）**

| 迁移 | 是否允许 | 谁触发 | `is_corrected` |
|---|---|---|---|
| `pending → taken / skipped / missed` | ✅ | `checkin.submit`（含老人自己打卡） | `false`（`taken` 且主动标记的记 `self`） |
| `missed（系统判定, is_corrected=false） → taken` | ✅ | `checkin.submit` | `true`，`checked_by='manual'` |
| `taken → missed / skipped` | ✅ | `checkin.correct`（仅 admin/member） | `true` |
| `pending → missed / skipped` | ✅ | `checkin.correct` | `true` |
| **`missed（已人工改判, is_corrected=true） → taken`** | ❌ **服务端拒绝 1005** | — | — |
| **`is_corrected=true` 的行再次 `correct`** | ❌ **拒绝 1005** | — | — |

一句话记法（UI 的原话，我照抄因为这是最不易误解的表述）：**系统判的漏服可以救，人判的漏服不能翻。**
这样既堵住了"来回改两次把完成率刷到 100%"的口子，又不会把管理员锁死在一个错误的系统判定上 —— 冻结表字面写的"只允许 taken→missed/skipped 单向"如果照字面实现，管理员就无法纠正系统误判，那是另一个方向的错误。

**完成率口径（硬规则，不接受讨论）**
```
完成率的分子分母都只含：系统判定 + 老人自主打卡（checked_by='self'）
manualCorrectCount 单列返回，明确不计入完成率
```
理由：不锁死口径，子女改两次就能把完成率刷到 100%，北极星指标当场作废。

## 四、提醒调度架构 ★ 本方案核心

### 4.1 问题拆解

| 约束 | 后果 | 应对 |
|---|---|---|
| 定时触发器最小粒度 1 分钟 | 无法为"8:00/8:30/12:15"各建一个触发器 | 不按时间点建触发器，**按分钟扫时间桶** |
| 用户时间点任意、可随时改 | 无法预编译出有限的"时间槽" | 落到 `due_ts`，索引即槽位 |
| 早药集中在 7:00–9:00（约 40% 日剂量） | 8:00 那一分钟可能 4,000+ 条，单实例扛不住 | **推送与扫描解耦**：tick 只入队，worker 分片消费 |
| 一次性订阅额度有限 | 推不出去就白扫 | 额度池 + 四级降级（见第六节） |
| 云函数按调用次数计费 | tick 每天 1440 次是固定成本 | tick 保持极轻（<200ms、不调微信 API） |

### 4.2 核心思路一句话

> **把"提醒时间"物化成带确定性主键的 `dose_logs` 行，让数据库索引充当时间轮的槽位；每分钟的 tick 只做一次 1 分钟宽度的索引范围查询并入队，真正的推送由分片 worker 从队列拉取消费 —— 扫描与发送彻底解耦，靠"确定性 _id + 条件更新 CAS"实现三道幂等。**

不用 Redis、不用时间轮内存结构、不扫全表。1 分钟分桶天然落在 `due_ts` 索引上。

### 4.3 三段式流程

```
【阶段 0】materializer  cron: 0 10 0 * * * *  (每天 00:10)
  扫 plans（status=active 且 start_date <= 明天）
    → 按 plan_id hash % 4 拆 4 片，并行 4 个云函数实例
    → 为明天每个 time 生成一条 dose_logs：
        _id = `${plan_id}_${due_date}_${due_minute}`   ← 幂等锁 ① 重复执行只会 duplicate key
        status='pending', remind_status=0, alert_status=0
    → 单实例 200 条/批 add，捕获 duplicate 错误静默跳过
    → 周期用药 cycle_end_date < 明天 → plans.status='finished'，不再生成
  耗时：DAU 1 万时约 1.3 万条 / 4 片 = 3,300 条/片，约 1.8s/片

【阶段 1】reminder-tick  cron: 0 */1 * * * * *  (每分钟，唯一高频触发器)
  T0 = now（UTC ms），窗口 [T0, T0+60000)
  ── 1.1 常规提醒入队 ──
  query: due_ts ∈ [T0, T0+60s) AND status='pending' AND remind_status=0  (limit 1000)
    → 按 openid 聚合，同一人同分钟的多个药合并成一条消息（省 20~30% 推送量，老人也更好读）
    → 写 push_tasks（_id = md5(openid+分钟桶+tmpl_key)）← 幂等锁 ②
    → 入队前先做额度预算：额度不足时只保当日最早 1 个 slot，其余 remind_status=3（见 6.2.1）
    → 若本分钟任务数 > 200：拆 8 片，callFunction('push-worker',{shard:i}) × 8 并发（不 await）
      否则：本函数内直接消费（省调用次数）
    → 条件更新 dose_logs：where(_id ∈ ids, remind_status=0).update(remind_status:1)（标记已入队）

  ── 1.2 漏服兜底（每 tick 都跑，15 分钟滑动窗口）──
  query: status='pending' AND alert_status=0 AND due_ts ∈ [T0-3600s-900s, T0-3600s)
    → 写 push_tasks{priority:1, openid: 该家庭 admin_openids, tmpl_key:'MISSED'}
    → where(_id, alert_status:0).update({status:'missed', alert_status:1})  ← CAS 保证只通知一次
    → 窗口取 15 分钟而非 1 分钟，是为了容忍连续 tick 失败；靠 alert_status 幂等，重复扫无害

  耗时目标：< 250ms（128MB）。**tick 内绝不调微信发送 API。**

【阶段 2】push-worker  worker（事件触发，非 cron）
  入参 {shard}
    → 拉 push_tasks: status='queued' AND shard=${shard} AND next_retry_at<=now
       order by priority asc, next_retry_at asc，limit 40
    → 逐条：CAS 置 sending（where(_id,status:'queued').update → stats.updated==1 才继续）
    → 查 subscriptions.quota：0 → 直接 dropped，写 dose_logs.remind_status=3
    → subscribeMessage.send（page 直达打卡页，data 精简）
    → 成功：status='sent'、quota-1、dose_logs.remind_status=1
    → 失败：按 errcode 分类（见 4.5）
  单条 40ms，40 条 ≈ 1.6s（256MB）
```

### 4.4 为什么不是别的方案

| 备选 | 否决理由 |
|---|---|
| 每 tick 扫全表 `status='pending'` | 450 万行表，每分钟一次全表扫描 = 数据库成本爆表 + 超时 |
| 按时间点建多个 cron 触发器 | 时间点任意且可改；云开发单函数最多 10 个触发器；根本表达不了 |
| 前端定时器 + 本地提醒 | 小程序退出即失效，老人不会常驻；不能通知家属，产品价值归零 |
| 自建 Redis / 时间轮内存结构 | 云开发无 Redis，自建违反"零运维"；且我们的"时间轮"就是 `due_ts` 索引，**不需要内存结构** |
| 数据库触发器 | 云开发 DB 触发器不支持"按时间条件触发"，只能集合写入触发 |
| 只靠"用户打开小程序时补推" | 老人一天只打开 2 次，漏服兜底完全失效 |

### 4.5 失败重试与降级判决表

| errcode | 含义 | 决策 |
|---|---|---|
| 43101 | 用户拒收 / 无可用额度 | `dropped`，**不重试**，对应池 `quota=0`、`mainSwitch=false`，`dose_logs.remind_status=3`，给前端打"需重新订阅"标 |
| 47003 | 参数错误（模板字段类型不符） | `dropped` + 立即告警（**这是代码 bug，不是运行时问题**） |
| -1 / 45009 | 系统繁忙 / 接口频率限制 | 重试，`retry_count+1`，`next_retry_at = now + 60×retry_count` 秒，最多 3 次 |
| 40003 | invalid openid（已注销） | `dropped`，`users` 标 `unreachable` |
| 其他 | | 最多重试 2 次 |

重试耗尽 → `failed`，写 `dose_logs.remind_status=2`，靠"首页红点 + 打卡页未完成卡片"兜底（见第六节 L3/L4）。

### 4.6 三道幂等锁（逐层说明为什么够）

| # | 位置 | 机制 | 防的是什么 |
|---|---|---|---|
| ① | 生成 | `dose_logs._id` = plan+日期+分钟，确定性 | materializer 重跑/分片重叠 → 不会产生重复剂量行 |
| ② | 入队 | `push_tasks._id` = md5(openid+分钟桶+模板) | tick 重试、多实例并发扫到同一批 → 同一人同一分钟只有一条任务 |
| ③ | 发送 | `update({status:'queued'})` 后校验 `stats.updated===1` | worker 被并发调用 → 只有一个实例能把 queued 改成 sending |

云开发单文档 `update` 是原子的，`stats.updated` 就是可靠的 CAS 返回值 —— 这是不引入 Redis 也能做分布式锁的关键。

### 4.7 定时触发器配置（可直接粘到控制台）

| 函数 | cron（7 段：秒 分 时 日 月 周 年） | 说明 |
|---|---|---|
| `reminder-tick` | `0 */1 * * * * *` | 每 1 分钟 |
| `materializer` | `0 10 0 * * * *` | 每天 00:10 生成次日剂量 |
| `archive` | `0 30 3 * * * *` | 每天 03:30 归档 + 重算缓存 |
| `weekreport` | `0 0 20 * * 0 *` | 每周日 20:00 发周报 |
| `warmup` | `0 */5 * * * * *` | 每 5 分钟预热 `schedule`/`notify`/`checkin`，压首屏冷启动 |

注意事项：
- 云开发控制台 cron 为 7 段，秒位必须写 `0`；若某版本报字段数错误，改 6 段 `*/1 * * * * *`。
- **单个函数最多 10 个定时触发器**，所以"一个时间点一个触发器"的路走不通，本方案只用 5 个。
- 触发器时区为 UTC+8，但**函数内 `new Date()` 是 UTC**，务必用 `bjNow()` 工具函数。
- 一个可选的省钱变体（**P0 不做，记下即可**）：夜间 `0 */5 0-5 * * * *` + 白天 `0 */1 6-23 * * * *`，省 20% 调用量，代价是夜间提醒最多延迟 5 分钟。DAU 3 万时 tick 只占 4% 调用量，不值得为 20% 牺牲确定性。

### 4.8 "计划变更"与"稍后提醒"的处理（两个易漏场景）

- **改时间**：`plan` 云函数在 `times` 变更后，删除「该 plan + 今天 + `due_ts > now` + `status='pending'`」的旧行，重新生成新行。**已打卡的行绝不删**（这是审计与完成率的分母）。
- **稍后提醒（15 分钟）**：不建独立队列 —— 直接把该 `dose_log.due_ts += 900000`、`remind_status=0`、`snooze_count+1`（上限 2 次）。**扫描条件只有 `due_ts` 一个，架构复杂度砍半。**
- **"今天不吃"**：`status='skipped'`，`skip_reason` 必填；不计入漏服，不计入完成率分母（或单独记为"主动跳过"，周报拆开展示）。

**`recentView`（已读回执，增长 P1）**：`schedule.today` 的顶层字段，取 `dose_views` 中「昨天、非本人、role≠elder」最近一条 → `{alias:"女儿", at:时间戳}`；没有则 `null`。老人端只渲染一行灰字「昨天女儿看了你的记录」，**不做红点、不做弹窗、不做声音**。读取成本 = 1 次单文档读，可忽略。

**`dose_text` 的格式化规则（谁负责）**：**后端统一出，前端不做任何中文映射。** 但规则是"**原样透传 + 缺省补齐**"，不是数值转中文：
1. `dose_text = plan.slots[i].d || medicine.default_dose || ""`；
2. **后端不解析数值、不做单位归一、不做 `0.5 → "半片"` 转换**。`0.25片`、`1.5片`、`半片`、`1片半` 都真实存在，任何转换规则都会在某处出错，而**剂量显示错是这个产品最不能犯的错**（主理人已采纳此版）；
3. `d` 与 `default_dose` 都空（脏数据）→ 兜底 `""`，前端隐藏剂量行而不是显示 `undefined`；
4. **`dose_logs` 冗余快照 `dose_text`**：子女后期改剂量，历史记录必须显示"当时吃的是多少"（用药史可追溯性），不能 join 现算；
5. 输入侧由 UI 快捷 chip 兜住（`1片 / 半片 / 2片 / 自定义`），**预设快照落在药品层**，不随药名变。

**`checkin.submit` 的批量语义（冻结表 §7，与前端出队规则对齐）**
- `applied[].changed`：`true`=本次真正写入；`false`=**幂等空操作**（之前已是该状态）。**前端两种都出队**（结果已确定，重投无害、不卡队列）。
- `rejected[]`：仅 `code=1005`（invalid）与 `1003`（not_member）**留队并提示用户**，其余按错误码处理。
- **部分成功合法，绝不整批回滚**；**前端单批 ≤8 条，服务端 >8 直接 1005**。
- 幂等三部曲：`idem_keys`（`idemKey` + 10 分钟 TTL，重投原样返回上次 `applied/rejected`）→ 逐条 CAS（`where(_id, status in ['pending','missed'] AND is_corrected=false)`）→ `stats.updated` 判定 `changed`。
- **允许的状态迁移**（严格按冻结表 §7）：`pending → taken|skipped|missed`；**`missed → taken` 允许**（老人补吃，兜底路径的一部分，不是异常分支）**但必须 `is_corrected=false`** —— 已被人为改判为漏服的行，`submit` 不得再翻回 `taken`（见 §3.14 第 5 条）；`taken → missed|skipped` **仅经 `checkin.correct`，且不可逆**。

**`checkin.correct` 服务端契约（这条是全案最后补的一项，也是防刷北极星的关键）**
```
入参：{ dose_id, to_status: 'missed' | 'skipped', reason? }
出参：{ ok: true, is_corrected: true }
```

| 不可逆 | 已是 `is_corrected=true` 的行**拒绝再次修改**（防来回刷） | `1005` |

| `warmup` | cron 每 5 分钟 | 预热 `schedule` / `notify` / `checkin` 容器，压冷启动抖动 | `{}` | 288/日，80ms |

> 预热说明：云开发不承诺实例复用，预热只能降低（不能消除）冷启动概率，真正兜底是前端 `storage` 缓存 —— **两边都做**，成本 288 次调用/日可忽略。

## 六、订阅消息额度管理

### 6.1 现实约束
一次性订阅消息：用户**主动点击授权 1 次 = 可下发 1 条**，授权可累计；`wx.requestSubscribeMessage` 一次最多 3 个模板，用户勾"总是保持"后不再弹。长期订阅消息需特定类目，个人主体拿不到。

### 6.2 四个独立额度池（key 与前端一致：`CHECKIN` / `MISSED` / `WEEKLY` / `RECHECK`）
| tmpl_key | 模板 | 接收人 | 授权时机（决定池子能不能养活） |
|---|---|---|---|
| `CHECKIN` | 服药提醒 | 服药人 / 其绑定 openid | **① 打卡成功态的任意一次 TAP 内静默续订**（见下方修正）② 建药成功页主按钮 ③ 额度 ≤1 时的顺手续订按钮 |
| `MISSED` | 家人漏服预警 | 家庭管理员 | **① 接受邀请加入家庭成功时**（动机最强）② 创建家庭完成时 |
| `WEEKLY` | 每周服药报告 | 家庭成员 | 周报页"订阅下周报告"按钮 |
| `RECHECK` | 复诊提醒（**P1**） | 服药人家属 | **复诊报告导出成功后**（用户刚拿到报告、动机最强）。独立触点，因为微信一次最多 3 个模板，挤不进上面那一批 |

> ⚠️ **本方案 v1.0 在此处写错过一次，已由前端纠正（重要，记录防止再犯）**：原文写"打卡成功后立刻请求授权"是**技术上不成立的** —— `wx.requestSubscribeMessage` 必须由**用户 TAP 手势**同步触发，一旦进入 `callFunction` 的 success 回调（异步栈）就会直接 `fail: can only be invoked by user TAP gesture`。正确做法是前端的**四态授权状态机 + 静默续订**：已勾选"总是保持以上选择"的用户（`getSetting` 判定 `itemSettings[tmplId]==='accept'`）调用时**不弹窗、直接 accept**，因此在打卡成功态的任意一次点击（"返回今日"/撤销）内同步调用即可零打扰 +1 额度；未勾选者一律走底部卡片（用户点按钮才弹窗）。这个机制比我原来的写法更强：弹窗只出现一次，之后全靠静默续订维持额度池日清日结。

一次 `wx.requestSubscribeMessage` 正好请求 3 个模板（微信上限 3），`notify.ack` 每回填一个模板 +1 —— 这是额度模型唯一的写入入口。

**为什么必须分开**：漏服预警是产品的核心价值（PRD 场景 C），如果和常规提醒共用一个额度池，早药提醒会把额度吃光，漏服通知就发不出去 —— 等于自杀。分开后，`MISSED` 池极省（每人每天 0~1 条），能长期稳定存活。

**额度自繁殖**：`CHECKIN` 每天消耗 2.5 条，打卡成功每天回填 2.5 条 —— 只要用户真的在打卡，额度池就是**日清日结的正循环**。这是本方案能长期跑通的根本原因。

### 6.2.1 额度不足时的保命策略：只保"当日最早一次"（与前端约定一致）
`reminder-tick` 在入队前对每个 openid 做一次额度预算：

```
剩余可推次数 = quota.CHECKIN
今日剩余待推 slot 数 = n
if quota.CHECKIN >= n        → 全推
else if quota.CHECKIN >= 1   → 只推当日最早的 1 个 slot，其余 remind_status=3（降级）
else                         → 全部降级，仅靠前端主动打开补拉
```
理由：漏掉晚药还能靠"打开小程序看到红点"补，**漏掉早药当天就失去意义**。把稀缺额度压在最早那一次上，是留存最优解。`MISSED` 池不受此限制，永远不受常规提醒挤占。

### 6.3 用尽前的三级告警（阈值与前端 §9 一致）
| 阈值 | 动作 |
|---|---|
| `quota.CHECKIN <= 3` | 打卡成功页底部插入一行："明天的提醒快到期了，点一下续上"（不是弹窗，不打断） |
| `quota.CHECKIN == 0` 且 `mainSwitch` 开 | 看板常驻 `quota-tip`（每日 ≤1 次）+ tabBar 红点；打卡成功后顺带一次授权 |
| `quota.CHECKIN == 0` 且连续 3 天未回填 | 用 `MISSED` 池给管理员推一条："爸爸的提醒已失效 3 天，请打开小程序恢复" |

`mainSwitch` 是**推断值**（微信不提供总开关查询接口）：`ack` 收到 accepted 置 `true`；推送返回 `43101` 且用户从未 ack 过置 `false`。前端仅在 `mainSwitch=true` 时展示常驻引导，避免对已永久拒收的用户反复骚扰。

### 6.4 额度不足时的四级降级阶梯
| 级别 | 手段 | 成本 | 覆盖场景 |
|---|---|---|---|
| L1 | 订阅消息送达 | 免费 | 正常态 |
| L2 | 小程序内红点 + 打卡页"待服"卡片置顶 + `schedule.today` 返回已过点项（前端本地 diff 出漏服） | 免费 | 用户会主动打开 |
| L3 | 漏服时改推管理员（`MISSED` 池，独立于 `CHECKIN`） | 免费 | 服药人无额度但管理员有 |
| L4 | 管理员端"一键拨打电话"（`wx.makePhoneCall`，号由管理员自己存） | 免费 | 全无额度时的最终兜底，**符合"工具不替代医疗"的定位** |

注：短信通道明确不做（PRD 已排除，成本 0.03 元/条 × 数万条 = 直接吃光广告收入）。

|---|---|---|---|

### 7.2 云开发数据库权限配置（可直接粘）

云开发集合权限分四档：`仅创建者可写`/`仅创建者可读写`/`所有用户可读`/`所有用户不可读写`，外加**自定义安全规则**。本方案绝大部分走自定义规则 + 云函数。

```jsonc
// users —— 只能读自己的，写全部走云函数
{ "read": "doc._id == auth.openid", "write": false }

// medicines_common —— 常用药预设，公开只读
{ "read": true, "write": false }

// 以下全部为「所有用户不可读写」，只能被云函数以 admin 权限访问：
// families / family_members / patients / medicines / plans /
// dose_logs / subscriptions / push_tasks / orders / entitlements /
// weekly_stats / daily_board_cache / audit_logs / ad_events / app_config
{ "read": false, "write": false }
```

**为什么不写更精细的安全规则（比如按 family_id 过滤）**，三条硬理由：
1. **表达能力不够**：安全规则无法表达"我的 role 是 admin 且该 patient 属于我的家庭且我的会员等级允许第 4 个药品"这种复合条件。写不出来，就只能靠云函数。
2. **规则校验本身要花钱**：自定义规则的 `get('database.family_members.xxx')` 会在每次请求时触发额外数据库读，读操作计费 + 延迟增加。
3. **一次写错就是全量泄露**：规则里少写一个 `&&`，全站健康数据裸奔。云函数的鉴权只有一处代码，review 得过来。

### 7.3 云函数侧统一鉴权中间件（唯一真相源）

```js
// common/auth.js —— 所有涉及 family 的云函数第一行都调它
const db = cloud.database()
const _ = db.command

async function assertMember(familyId, openid, needRole = 'elder') {
  // _id 是复合主键，单文档读，最快
  const key = `${familyId}_${openid}`
  let doc
  try { doc = (await db.collection('family_members').doc(key).get()).data }
  catch (e) { throw { code: 403, msg: '不是该家庭成员' } }   // 越权：统一 403，不泄露"家庭是否存在"

  const RANK = { elder: 1, member: 2, admin: 3 }
  if (RANK[doc.role] < RANK[needRole]) throw { code: 403, msg: '权限不足' }

  // elder 只能操作 patient_id == 自己绑定的那个
  if (doc.role === 'elder' && doc.self_patient_id) return { ...doc, scope_patient: doc.self_patient_id }
  return doc
}
```

调用示例（打卡）：`checkin.submit` 逐条读出 `dose_log` → `assertMember(dose.family_id, OPENID)` → 若 `role==='elder'` 且 `dose.patient_id !== self_patient_id` → 该条进 `rejected[{code:1003}]`（**单条失败，整批不失败**），其余条目照常处理。

**`checkin.correct` 的角色校验（主理人特别要求，写进 `assertMember` 的调用处）**
```js
// correct 是唯一能人为改变完成率的入口，角色校验必须比其它接口更严
const m = await assertMember(dose.family_id, OPENID, 'member')  // member 已含 admin
if (m.role === 'elder') throw { code: 1003, msg: '老人端不提供改判入口' }
// 注意：老人端 UI 不给按钮，但服务端绝不能依赖"前端不会调"
```

### 7.4 为什么不能只靠前端校验（给主理人的一句话解释）
小程序前端就是一段 JS，攻击者用开发者工具或抓包改一行 `where` 条件就能换掉 `family_id`；`openid` 虽是服务端注入不能伪造，但**"这个 family_id 是不是我的"这个判断如果放在前端，就等于没有**。云开发的数据库权限是集合级的粗粒度开关 —— 一旦为性能放开"所有用户可读"给 `dose_logs`，任何人遍历 `family_id` 就能拉到别人家老人吃什么药。这属于 PRD 第八节明确点名的敏感健康信息，一次泄露就是封号 + 法律责任。**所以：写操作全部云函数，校验只有一处代码。**

补充：所有越权失败（`403`）写 `audit_logs`，含 `openid / family_id / 函数名 / 时间`，用于发现扫描行为。

### 7.5 角色细化：`elder` 的数据范围（需要 `family.info` 配合）
`elder` 的 `self_patient_id` 存在 `family_members` 上。为让前端在 `family.info` 一次拿到"我是谁对应的哪个服药人"，**出参必须带 `selfUid`**（见 5.1）。否则老人端无法只展示自己的卡片，会看到全家的药 —— 既是体验问题也是权限问题。

| 云函数资源使用量 | 0.000111 元 / GBs | 40 万 GBs |
| 数据库读操作 | 0.015 元 / 万次 | 500 万次 |

### 9.2 成本纪律（唯一一条，写死，验收必查）

> **任何图片上传前必须压缩到 ≤60KB（最长边 ≤1280），前端 `wx.compressImage` + WebP。云开发存储 0.043 元/GB/月 + CDN 回源 + 下行流量，未压缩的手机原图是账单从 31 元冲到 300 元以上的唯一主因。**
>
> 这条不是建议、是验收项。它比文档里任何后端优化加起来都值钱：一张 2MB 原图 = 33 张 60KB 图的成本，而药盒照、头像、分享卡片封面加起来人均 3~5 张。**宁可牺牲清晰度，不可牺牲这条** —— 用户看的是"哪个药盒"，不是药盒上的防伪标。

### 9.3 用量模型（把乘法写出来，便于复核）

**推导链**：
```
家庭组   = DAU / 2.8        DAU 1 万 → 3,571 组
服药人   = 家庭组 × 1.5      → 5,357 人
日剂量   = 服药人 × 2.5 次   → 13,400 条/天
净推送   = 日剂量 × 0.86     → 11,524 条/天（同人同分钟多药合并，砍 14%）
```

**云函数调用次数的真实构成（DAU 1 万）**：

| 来源 | 计算式 | 次/月 |
|---|---|---|
| 前端 API（最大头） | 1 万 DAU × 5.5 次/天 × 30 | **1,650,000** |
| `push-worker`（**批处理**） | 11,524 条/天 ÷ 40 条每调用 × 30 | 8,600 |
| `push-worker`（**峰值分片**：每日 4 小时按 8 分片） | (240 分 × 8 + 1,200 分 × 1) × 30 | 93,600 |
| `reminder-tick` | 1,440 × 30 | 43,200 |
| `warmup` | 288 × 30 | 8,640 |
| `weekreport` / `materializer` / `archive` | — | 2,350 |
| **合计** | | **≈ 181 万次/月** |

> **关键点：订阅消息不是"一条一次云函数调用"。** 一次 `push-worker` 调用里连续发 40 条订阅消息，40 条只计 1 次调用。如果主理人按"30,000 条推送 = 30,000 次调用"来估，会高估 40 倍。真正的成本大头是**前端 API 调用**（165 万次/月，占 91%），不是推送。

| 项目 | 用量/月 | 免费额度 | 超量 | 超量费用 |
|---|---|---|---|---|
| 云函数调用 | 181 万次 | 100 万 | 81 万 | 81 × 0.0133 = **1.08 元** |

**为什么"基准"和"保守"差 5 倍 —— 三个真实的失控点**（这才是该盯的地方）：

| 失控点 | 基准做法 | 不做会怎样 | 差额 |
|---|---|---|---|
| **药盒照片不压缩** | 上传前 `wx.compressImage` + 转 WebP，压到 ≤60KB | 单张 600KB–2MB，10 倍体积 → 存储与 CDN 同时爆 | **+100~300 元/月** |
| **CDN 流量无节制** | 列表页只用缩略图（≤20KB），大图点开才加载；`fileID` 带版本号长期缓存 | 每次进看板拉原图，流量 10 倍 | **+50~100 元/月** |
| **看板不做缓存** | `daily_board_cache` 把一次看板 15 篇文档读压到 1~2 篇 | 读操作 1,350 万/月，超 850 万 × 0.015 | **+13 元/月**（金额小，但延迟会拖慢首屏） |

**关于 19.9 元套餐的具体配额 —— 我必须说明白**：微信云开发的计费形态近两年改过多次（免费额度制 → 按量计费 → 预付费套餐），各档套餐内含的具体调用量/容量配额**我无法离线确认，也不打算编一个数字给你**。请按下面这条判断，它不依赖具体配额：

> 我们的用量在**按量计费口径**下只值 11 元/月（DAU 1 万），因此：
> - 若 19.9 元套餐的配额 ≥ 我们的用量 → 实付 **19.9 元/月**（基准）；
> - 若套餐是**硬上限**（超了必须先升级 99 元档）→ 实付 **99 元/月**（上限）；
> - 若走纯按量、免费额度有效 → 实付 **0–11 元/月**。
> **三种情况的真值都在 0–99 元区间内，绝不会出现 300 元以上**（前提：图片压缩 + CDN 缓存 + 看板缓存三条纪律做到）。
> **给用户留预算建议按 150 元/月**：覆盖"套餐升一档 + 图片纪律偶有失守"的组合，留足安全边际。上线首月请到控制台账单页核对一次真实数字，1 分钟的事，比我任何估算都准。

**结论（给主理人做决策依据）**：
1. 后端成本在广告收入面前**不是变量**（占 1% 量级）。**不要为省后端钱做架构妥协**（不建索引、不归档、省调用次数），省下的几十块会被 bug 和延期吃掉几十倍。

3. 第二风险是 `dose_logs` 不归档：一年 470 万行后看板查询变慢，会逼你升套餐。`archive` 函数**必须在 M1 上线**。
4. 真正的业务风险仍是**订阅消息授权率**（PRD 假设 2：<40% 则提醒触达失效），这是产品问题，不是成本问题。

## 十、数据安全与合规

| 项 | 做法 |
|---|---|
| 健康数据加密 | 敏感字段（`medicines.name`、`patients.name`、`plans`、`dose_logs.drug_snapshot`）用 AES-256-GCM 应用层加密，密钥存**云函数环境变量**（不入代码库、不入前端）。代价：无法用这些字段做模糊搜索 —— 而我们本来就不做搜索，用 `_id`/索引字段查询不受影响。**注意 `_id` 里包含 `plan_id`，绝不含药名。** |
| 传输 | 云开发链路本身 HTTPS，不出微信内网 |
| 不采集 | 不取手机号（P0 不需要）、不取精确位置、不取通讯录、不取相册全量（`chooseMedia` 单张） |
| 隐私政策 | 首启弹窗「本工具仅提供服药提醒服务，不提供任何医疗建议，用药请遵医嘱」（PRD 8.3），同意后写 `users.disclaimer_agreed_at`，**留痕是免责的前提** |
| 最小可见 | 老人（`elder`）看不到其他家庭成员的用药记录；跨家庭数据在数据库层就物理隔离（全部集合前端不可读） |
| 越权防护 | 所有 `family_id` 入参强制 `assertMember()`；越权尝试写 `audit_logs`；`invite_token` 7 天过期 + 可重置 + 绑定使用次数 |
| 数据导出 | `account.export` → 生成 JSON 上传云存储，返回 24 小时有效的临时下载链接（含该 openid 在所有家庭组内的服药记录） |
| 注销 | 提交后 7 天冷静期（`users.delete_at`），到期由 `archive` 函数级联删除该 openid 在本家庭的数据；若其为 `families.owner` 且还有其他成员，先要求移交管理员 |
| 广告合规 | 云开发不做广告投放，但**流量主后台必须开启行业屏蔽**（医疗/药品/保健品，PRD 8.5）。后端在 `ad_events` 里记录 `ad_slot`，便于识别异常广告位 |
| 内容安全 | 药品名/备注为用户输入，写入前调 `security.msgSecCheck`（免费）；未通过则拒绝并提示"请填写规范的药品名称" |
| 未成年人 | 产品不面向未成年人，`users` 不采集年龄/生日 |

## 十一、运维与监控

**告警项（云开发监控 + 云函数内自检，触发即发管理员微信）**

| 指标 | 阈值 | 说明 |
|---|---|---|
| `reminder-tick` 连续失败 | ≥ 2 次 | **最高优先级，这个挂了全站提醒就死了** |
| `reminder-tick` 单次耗时 | > 1500ms | 索引失效或某分钟剂量异常多 |
| 单分钟扫描命中条数 | > 5000 | 数据异常（materializer 重复生成）或真实峰值，需扩容 worker |
| `push_tasks` 积压 | `queued` > 5000 或最老任务 > 10 分钟 | worker 不够或 API 被限流 |
| 推送失败率 | 1 小时 > 5% | 模板 ID/字段错、或大面积额度耗尽 |
| 43101 占比 | > 30% | 额度管理出问题，用户授权转化崩了 |
| 云函数错误率 | > 1% | |
| 数据库容量 | > 套餐 80% | 归档函数没跑 |
| `audit_logs` 越权数 | 单 openid 1 小时 > 20 | 疑似扫描攻击 |

**日志**：云函数统一 `logger.info/error`，带 `trace_id = 函数名:openid:时间戳`；错误日志含入参脱敏副本（药名脱敏为 `***`）。云开发日志保留 7 天，关键业务流水（打卡、权益发放）另存 `audit_logs` 长期保留。

**备份**：云开发数据库支持自动备份（每日一次，保留 7 天，控制台可恢复）；另每周 `archive` 后导出一次 `weekly_stats` + `users` 到云存储冷备（成本几毛钱），防误删。

**灰度**：小程序没有服务端灰度，用**功能开关表** `app_config.features = {ad_slot_D_enabled, badge_enabled, ...}` 从云端下发，出问题改配置即时生效（不用发版）。云函数用版本别名 `prod` / `gray`，新函数先在小流量 openid 尾号 `% 100 < 5` 的请求上走 gray 版本。

**备份发布节奏**：materializer / archive / reminder-tick 三个函数改动必须先在测试环境用真实历史日期回放一遍（造 10 个家庭 × 30 天数据，验证剂量条数一致、无重复 _id）。

### 14.4 契约层面已确认的 7 处设计（冻结表未覆盖、但已与三方对齐）

1. **`dose_logs.status` 只有四值** `pending/taken/missed/skipped`，迟到用 `is_late` 布尔 —— 原五值枚举会让前端 `switch` 落到 default 分支（主理人已终裁采纳此版，前端副行显示"晚服 12 分钟"、配色复用已服绿）。
2. **打卡允许 `missed → taken`**（CAS 条件 `in ['pending','missed']`）。老人 10 点补吃是真实场景，原来会误拒，等于把兜底路径打死。
3. **不设 `take_batch`**：`checkin.submit{items[]}` 天生批量，部分成功合法，`applied[].changed` 区分真写/空操作。前端已确认接受（主理人亦认可"能力保留、接口收敛"）。
4. **额度三池 + "只保当日最早一次"策略**（§6.2.1），给了确定算法，不是"降级"两个字。

6. **`slots` 改为对象数组**（`{t,d,key}`），支持"早 1 片晚半片"；`dose_text` 快照进 `dose_logs`（用药史可追溯）。
7. **漏服预警收件人必须是显式 admin**（`families.owner_openid` 或 `role==='admin'`），**不能用"第一个加入的人"** —— 多 guardian 家庭会推错人，UI 的「提醒他」按钮同理。

### 14.5 `checkin.correct` 的两条口径我必须说明（冻结表字面 vs UI 更正）

冻结表 §7 写的是"**只允许 `taken → missed/skipped` 单向、不可逆**"。UI 的 v1.2 更正版给了一个更细的状态机：**系统判的漏服可以救，人判的漏服不能翻**。

我按 **UI 的更正版**实现，理由：照冻结表字面实现，管理员就**无法纠正系统误判**（"他确实吃了只是没打卡"是最常见的场景），那是另一个方向的错误 —— 冻结表的意图是"防来回刷数据"，UI 的版本完整保留了这一点（已 `is_corrected=true` 的行不可再改、不可翻回 `taken`），同时放开了正确的纠错路径。

实现落在 §3.14 的状态机表，逐条可对。**如果主理人认为必须严格按冻结表字面执行，请回一句，我把"系统判漏服 → taken"这条也关掉** —— 但那样 UI 的纠错入口就只剩单向，请一并确认是否接受。

### 14.7 平台限制与主理人加的两条硬规则（保留为最高风险项）

**`ad.unlock` 无法验证用户真的看完了广告** —— 微信激励视频没有服务端回调，`proof.ts` 由前端提供，可伪造。**刷量在技术上无法杜绝**，只能压住频率：

| 防线 | 规则 | 依据 |
|---|---|---|
| 唯一键防重 | `md5(openid+product_id+floor(ts/30000))`，30 秒窗口内同产品只成功一次 | §3.10 |
| 时间戳校验 | `proof.ts` 与服务器时间偏差 ≤ 90s，否则拒绝 | §3.10 |
| **单用户单日总上限** | **≤ 5 次**（所有 product 合计） | 主理人要求 |
| **单用户单产品日上限** | **≤ 2 次** | 主理人要求 |
| 超限行为 | **直接返回失败 + 写 `audit_logs`**，不暴露具体阈值给前端 | 主理人要求 |
| 比值监控 | `unlock次数/激励视频曝光次数`、`reward_grant/reward_start`，异常高即被刷 | 增长侧埋点 |

> 🔴 **最高风险项（写死，不许后来者改）**：**未来接入真实支付时，权益发放必须由支付回调（`pay_notify` 验签 + 幂等）驱动，任何情况下不得复用 `ad.unlock` 的"前端凭证信任"模型。** 广告激励的凭证信任能成立，仅因为标的物是"免广告/多看一份报告"这类零边际成本权益；一旦标的物变成用户付了钱的东西，同一套信任模型就是资金漏洞。此条同时列在 §十二 留口子清单的**最高风险行**。

## 十五、订阅消息模板申请表（M1 第一周照此提交）

**前置**：小程序后台类目须为「工具 - 效率」（或「工具 - 健康管理」若可选），**不得选医疗服务类目**；订阅消息类型选**一次性订阅**（个人主体无长期订阅资格）。

### 15.1 四个模板的字段定义（前 3 个 P0，第 4 个 P1）

| # | 模板标题 | 关键词（字段类型 · 长度上限） | 可填空 | 示例文案 | 备注 |
|---|---|---|---|---|---|
| 1 | 服药提醒 | `服药人`(name,10字) / `药品名称`(thing,20字) / `服药时间`(time) / `温馨提示`(thing,20字) | 第 4 项可空 | 「爸爸 · 苯磺酸氨氯地平片 · 08:00 · 饭后服用」 | **合并推送时药名必须 ≤20 字**，超出截断为"氨氯地平片等3种药"（见 15.3） |
| 2 | 家人漏服提醒 | `服药人`(name,10字) / `服药时间`(time) / `药品名称`(thing,20字) / `未服时长`(phrase,5字) | — | 「爸爸 · 08:00 · 氨氯地平片 · 超1小时」 | `phrase` 只有 5 个汉字，**写"超1小时"不要写"已超过1小时未服用"** |
| 3 | 每周服药报告 | `服药人`(name,10字) / `完成率`(number,32位) / `漏服次数`(number,32位) / `统计周期`(phrase,5字) | 第 4 项可空 | 「爸爸 · 92 · 3 · 本周」 | 完成率只传数字（不带 `%`），`%` 在模板正文里写死 |
| 4 | 复诊提醒（P1） | `服药人`(name,10字) / `复诊时间`(time) / `提醒事项`(thing,20字) | — | 「爸爸 · 3月15日 09:30 · 带上服药记录」 | 增长侧用于"复诊前 1~2 天"推送，**不写"该复查了"之类的医疗判断**，只传用户自己填的复诊时间 |

> 第 4 个模板**不能与 1~3 同批请求**：微信 `requestSubscribeMessage` 一次最多 3 个模板，所以 `RECHECK` 走独立触点（复诊报告导出成功后），独立额度池，不与常规提醒抢额度。

### 15.2 为什么"一次提交后不能改"（这是必须理解的核心约束）

1. **字段类型在模板创建时固化**：`send` 时 `data` 的结构必须与模板字段一一匹配，类型不符直接返回 **`47003` 参数错误**。微信没有"修改模板字段"的接口，只能**删除模板 + 重新申请一个新模板 ID**。
2. **旧模板 ID 会立即失效**：删除后旧 `tmpl_id` 再发就是 `47003`，已发出的历史消息不受影响，但新消息全废。
3. **所以模板 ID 绝不能写死在前端或代码里** —— 这正是 `config.tmplIds` 存在的唯一理由：换模板时改 `app_config` 一个字段即可热切换，**小程序不用发版、用户无感**。§5.1 的 `tmplIds{CHECKIN,MISSED,WEEKLY}`（第 4 个 `RECHECK` 见 §14.3 待签） 请前端务必从 `config` 读。

### 15.3 提交时的 4 个细节（决定会不会被打回）

- **药名长度**：按人合并推送后，一条消息可能带 2~3 个药名。`thing` 只有 20 字 → 后端做截断策略：1 个药名全写；2 个全写（多数不超）；3 个及以上写"首个药名等 N 种药"。**这条必须写进 `push-worker` 的实现，否则 47003 会在早药高峰期集中爆发。**
- **文案禁区**：模板正文和示例里**不出现**"治疗""疗效""推荐用药""替代医生""按时服药可控制血压"等表述（PRD 第八节）。写"该吃药了""提醒您服药"是安全的。
- **不要写"请服药"以外的医疗动作**：例如"服药后测量血压"这类引导会被判为医疗建议，删掉。
- **每个模板只讲一个用途**：分两批申请 4 个模板（1~3 同批，第 4 个 P1 单独提），不要试图用一个模板覆盖多个场景 —— 这也是前端 §14 C4 裁决"一次只弹 1 个"能够成立的前提。

### 15.4 申请节奏与验收

| 步骤 | 时间 | 产出 |
|---|---|---|
| ① 确认类目 + 订阅消息类型 | M1 W1 D1 | 后台截图存档 |
| ② 提交 4 个模板（用 15.1 的表直接填；1~3 同批，第 4 个 P1 单独提） | M1 W1 D1–D2 | 审核中 |
| ③ 审核通过（通常 1–2 工作日，被打回按 15.3 改） | M1 W1 D3–D4 | 4 个 `tmpl_id` |
| ④ 写入 `app_config.tmplIds` | M1 W1 D4 | 前后端同时可读 |
| ⑤ **用真实 `tmpl_id` 发一条测试消息** | M1 W1 D5 | 验证 `errCode:0`；若 `47003` 说明字段类型对不上，按错误提示的 `data` 逐字段比对 |

> ⑤ 是硬门槛：**在真实环境用真实模板 ID 发成功一次，这条链路才算通**。开发阶段用假 ID 时 `send` 会一直报参数错，很容易被误判成代码问题而白查半天。
